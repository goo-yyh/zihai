# 项目二维码目标设计方案

## 1. 目的与范围

本文定义 zihAI 项目二维码目标的产品规则、数据完整性、上传协议、审核生命周期、公开交互、清理顺序和验收范围，并作为实现与回归依据。

二维码用于小程序等没有公开网站或 GitHub 仓库的产品。它是网站 URL、GitHub 仓库之外的第三种项目目标，不是项目截图，也不能替代审核前仍然必需的 1～5 张截图。

本功能包括：

- 创建只有名称和描述、尚未填写目标的草稿。
- 在项目编辑页添加网站、GitHub 或二维码目标。
- 上传、查看、替换和删除一张项目二维码。
- 在首页卡片、公开详情页和管理员审核页查看二维码。
- 对二维码执行与其他公开项目字段一致的审核、缓存和 Blob 清理规则。

## 2. 数据模型与完整性

二维码是一对一存放在 `projects` 上的 Blob 引用：

| 字段             | 含义                          |
| ---------------- | ----------------------------- |
| `qrCodeUrl`      | 用于页面展示的公开 Blob URL   |
| `qrCodePathname` | 用于精确删除 Blob 的 pathname |

数据库必须保证：

1. `qrCodeUrl` 与 `qrCodePathname` 同时为空或同时存在，不能只保存其中一个。
2. 每个项目最多只有一张二维码。
3. 已保存的二维码 pathname 唯一，不能被两个项目同时引用。
4. 项目目标按状态执行下表约束。

| 项目状态   | 可以没有目标 | 目标要求                         |
| ---------- | ------------ | -------------------------------- |
| `draft`    | 可以         | 网站、GitHub、二维码可以全部为空 |
| `pending`  | 不可以       | 网站、GitHub、二维码至少一项     |
| `approved` | 不可以       | 网站、GitHub、二维码至少一项     |
| `rejected` | 不可以       | 网站、GitHub、二维码至少一项     |
| `archived` | 不可以       | 网站、GitHub、二维码至少一项     |

管理员驳回项目只改变审核状态并保留已提交的目标，因此 `rejected` 仍满足目标约束。Owner 随后编辑或删除公开字段时，`contentEditPatch` 会在同一个锁内更新中把项目从 `rejected` 转为 `draft`；该更新完成后，草稿才可以暂时没有目标。

历史迁移不得原地修改。实现必须从当前 Schema 生成新迁移，人工检查 SQL，并确认状态约束和二维码字段配对约束与本表一致。

## 3. 创建、编辑、提交与审核

### 3.1 创建草稿

创建项目时，名称和描述是必填项。网站 URL 与 GitHub URL 可以同时留空；创建成功后进入项目编辑页，由 Owner 继续添加网站、GitHub、二维码和截图。

草稿可暂时没有任何目标，但不能因此提交审核。界面提示只用于解释下一步，服务端和数据库约束才是最终边界。

### 3.2 编辑目标

网站、GitHub 与二维码可以任意组合。二维码存在与否必须从数据库中的受信字段判断，Server Action、Route Handler 或上传完成回调不得接受客户端提供的 Owner ID、pathname、审核状态或 `hasQrCode` 标记作为权威数据。

删除最后一个目标只在更新后的状态为 `draft` 时合法：

- `draft` 可以删除最后一个目标并继续保存。
- `rejected` 编辑时会由统一生命周期转为 `draft`，可以在同一更新中删除最后一个目标。
- `pending`、`approved` 或 `archived` 不能在没有替代网站、GitHub 或二维码的情况下删除最后一个目标。

### 3.3 提交与审核

提交审核必须在同一事务中锁定项目行，并重新检查：

1. 当前用户拥有该项目。
2. 项目当前状态允许提交。
3. 网站 URL、GitHub URL、二维码至少存在一项。
4. 项目拥有 1～5 张截图。

管理员批准项目时必须再次锁定项目行并重新检查目标和截图数量，避免上传回调、Owner 编辑或并发审核使先前读取失效。二维码不计入截图数量。

## 4. 审核生命周期

二维码是受审核的公开项目字段。上传、替换和删除二维码都必须与名称、描述、URL 和截图变更一样调用 `contentEditPatch`，不得在上传回调或 Action 中手写另一套状态分支。

关键结果包括：

- 修改 `approved` 项目的二维码会清空原批准和发布时间，并使项目回到 `pending`；重新审核前首页、公开详情和用户主页都不可见。
- 修改 `pending` 项目仍保持私密并更新统一审核状态。
- 修改 `rejected` 项目会清除驳回信息并回到干净的 `draft`，不会自动重新提交。
- 修改 `draft` 项目仍为 `draft`。
- `archived` 项目的结果以统一生命周期函数为准，不得仅在二维码流程中增加特殊状态分支；它仍必须满足非草稿目标约束。

所有公开查询继续只返回 `approved` 项目。二维码不得因为 Blob URL 可访问而绕过项目公开状态过滤。

## 5. 上传授权与文件策略

二维码复用现有 Vercel Blob 浏览器直传协议，不通过 Server Action 请求体传输原始文件。

文件策略如下：

| 项目     | 规则                                    |
| -------- | --------------------------------------- |
| 数量     | 每个项目最多 1 张二维码                 |
| MIME     | `image/jpeg`、`image/png`、`image/webp` |
| 大小     | 最大 5 MiB                              |
| 截图关系 | 独立计数，不占用 1～5 张截图额度        |

上传意图必须短时有效，并绑定：

- 当前已完成引导的用户。
- 目标项目。
- 服务器生成的精确 pathname。
- 签发时数据库中的二维码 pathname 与项目更新时间版本。
- 请求的 MIME 类型。
- 到期时间。

签发上传意图、Blob token 回调和上传完成接口都必须重新验证会话、项目所有权和绑定关系，Provider Token 与应用意图使用同一过期时间。完成接口还必须读取 Blob 报告的真实 metadata，验证真实 pathname、MIME 与大小，并保存 Provider 返回的规范 URL 后才能写入数据库。

## 6. 持久化、幂等与补偿

PostgreSQL 与 Vercel Blob 不能共享事务。二维码替换严格按以下顺序执行：

1. 浏览器把新二维码上传到新的 Blob pathname。
2. 完成服务验证签名意图、用户、项目、预期项目版本、pathname、MIME、大小和 Blob metadata。
3. 服务锁定 Owner 的项目行。
4. 在同一数据库事务中读取旧 pathname，原子替换 `qrCodeUrl` 与 `qrCodePathname`，并应用 `contentEditPatch`。
5. 数据库提交成功后，尽力删除旧 Blob。

失败处理：

- 新 Blob 无法持久化时，补偿删除这个新 Blob。
- 数据库已经引用新 Blob 后，旧 Blob 清理失败只记录服务端错误；不得删除新 Blob 或回滚已经提交的引用。
- 浏览器完成请求与 Vercel webhook 重复到达时必须幂等；相同 pathname 不重复改变状态或误删当前对象。
- 删除二维码使 pathname 再次为空后，旧意图仍会因项目版本不匹配而失败，不能复活已删除的对象。
- 并发替换必须通过项目行锁串行化，数据库最终引用的 pathname 不能被后到的旧对象清理删除。

删除二维码时，在项目行锁内清空成对字段并应用 `contentEditPatch`，提交后再尽力清理被解除引用的 Blob。若删除会使非草稿项目失去最后一个目标，操作必须以安全、可本地化的用户错误失败。

删除项目和删除账号时，必须在删除关系数据的同一数据库事务中锁定相关记录，并收集项目二维码以及既有头像和项目截图的精确 Blob pathname。事务提交后再尽力清理这些 Blob；清理失败只记录服务端错误，不恢复已经删除的关系数据。

## 7. 页面与交互

### 7.1 项目编辑页

编辑页在同一个“目标入口”卡片中展示网站 URL、GitHub 仓库和二维码，明确表达三者至少选择一项，同时继续允许任意组合。二维码不能再作为与 URL 入口平级的独立卡片。二维码区域需要提供上传、预览、替换、删除、进行中状态、成功反馈和安全错误反馈。

二维码上传成功不等于项目可提交；页面仍需独立提示 1～5 张截图要求。提交按钮的可用状态只能作为体验提示，服务端必须重新验证全部条件。

### 7.2 首页和用户主页卡片

有二维码的已通过项目在卡片图片右上角显示独立二维码图标。图标是查看按钮，不是外部导航链接；点击后打开二维码查看层，不能触发覆盖整张卡片的详情链接。

二维码按钮必须有可访问名称，并通过 `aria-haspopup="dialog"` 表达弹层语义。网站、GitHub 和二维码三种入口同时存在时均可独立操作，并在移动端保持可点击且不互相遮挡。

### 7.3 公开详情页

有二维码时，在点赞、建议、访问产品和查看代码所在的操作区增加查看二维码按钮。QR-only 项目也必须有明确的主要目标入口。

### 7.4 二维码查看层

卡片和详情页复用同一查看组件。查看层至少提供：

- 清晰、完整且不裁剪的二维码图像。
- 能替代图像含义的 alt 文本。
- `role="dialog"`、`aria-modal="true"` 和明确的对话框名称。
- 关闭按钮、背景关闭和 Escape 关闭。
- 打开后合理聚焦，关闭后把焦点还给触发按钮。
- 打开期间锁定背景滚动。

二维码图像应按原始内容清晰呈现，并用真实手机扫码验证，而不能只断言图片元素存在。

### 7.5 管理员审核页

管理员必须能在项目详情中查看二维码原图，再决定批准或驳回。审核页不可只显示网站和 GitHub，而遗漏 QR-only 项目的唯一目标。

## 8. 公开读模型与缓存

二维码 URL 必须贯通首页首屏查询、后续项目 API 分页、用户主页卡片、公开详情查询和管理员详情查询。客户端响应 Schema 与 TypeScript 类型必须允许 `qrCodeUrl` 为 URL 或 `null`，并拒绝字段形状不合法的响应。

二维码上传、替换和删除提交后，统一缓存 helper 必须失效：

- 首页项目列表。
- `/p/{projectId}/{slug}` 项目详情。
- `/u/{userId}/{username}` Owner 主页。
- 项目工作台和相关管理员页面。

二维码是展示字段，不改变项目规范 URL、Sitemap 路径或 Open Graph 主图；公开与否仍由项目状态决定。

## 9. 验收矩阵

### 9.1 目标与状态

- 名称和描述可以创建无目标 `draft`。
- 无目标 `draft` 不能提交。
- URL-only、GitHub-only、QR-only 以及任意组合都可提交。
- `pending`、`approved`、`rejected`、`archived` 无目标时由应用和数据库共同拒绝。
- `rejected` 编辑并在同一更新转为 `draft` 后，可以删除最后一个目标。
- QR-only 项目仍需 1～5 张截图；二维码从不计入截图数量。

### 9.2 上传与权限

- JPEG、PNG、WebP 在 5 MiB 内可上传，其他 MIME 或超限文件失败。
- 未登录、未完成引导、非 Owner、错误 projectId、pathname、MIME、签名或过期意图都失败。
- 同一项目始终最多引用一张二维码。
- 浏览器完成与 webhook 重复到达不会重复写入或误删。

### 9.3 生命周期与可见性

- 草稿二维码上传、替换和删除保持草稿。
- 已通过项目二维码变化后立即从所有公开查询隐藏并进入待审核。
- 驳回项目编辑后回到草稿并清除驳回状态。
- 管理员批准前重新检查目标和截图要求。

### 9.4 Blob 一致性

- 持久化失败会删除新 Blob。
- 替换成功后清理旧 Blob；旧 Blob 清理失败不影响新引用。
- 删除二维码、项目或账号时，提交后的 Blob 清理请求覆盖全部已收集的二维码 pathname；provider 清理失败只留下可观测的孤儿对象，不恢复关系数据，也不影响仍被数据库引用的新对象。
- 并发替换后数据库引用的最终 Blob 不会被补偿或旧对象清理误删。

### 9.5 页面交互

- 首页首屏、无限滚动后续页和用户主页的 QR-only 卡片都有二维码按钮。
- 卡片二维码按钮不会触发详情导航，网站和 GitHub 入口不受影响。
- 公开详情页和管理员详情页可查看二维码。
- 查看层的键盘关闭、焦点恢复、滚动锁、移动端/平板/桌面布局和真实扫码通过。

## 10. 完成门禁

实现完成前必须：

1. 为目标矩阵、生命周期、上传策略、授权、幂等、补偿、清理、公开响应和交互增加回归测试。
2. 运行 `pnpm format` 和 `pnpm check`。
3. 生成新迁移、人工检查 SQL，并运行 `pnpm db:check`。
4. 在隔离的 Preview 数据库与 Blob Store 完成 QR-only 全链路和真实扫码冒烟测试。
5. 确认没有修改可能已经进入共享环境的历史迁移。
